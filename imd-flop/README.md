# imd-flop

A reference build of the companion CLI from the "FLOP, by choice" proposal ([report, section F](https://github.com/Identity-md/research/blob/main/jobs/4bb06f36-c8da-4925-8e4d-378ed76cff68/files/artifacts/report.md#f-stopgap-imd-flop-companion-cli-spec)).
It gives one imd seat one FLOP identity, links the two with signatures, caps daily spend, runs model
calls for real imd jobs, and keeps a receipt next to each job. It does not change or wrap the imd worker.

Status: devnet rehearsal. The default provider is a **mock**, so everything below runs with no key,
no network and no spend.

## Commands

| Command | What it does |
|---|---|
| `init [--network devnet] [--seat <tokenId>] [--rotate] [--check-genesis]` | Makes one Ed25519 key for the seat (file mode 600, never printed). Prints the SS58 address (prefix 42, the devnet faucet's `ss58Format`) and the `did:key`. Refuses a second key for a seat unless `--rotate`, which writes a signed revocation record. `--check-genesis` compares the pinned genesis, the faucet's `/chain` genesis, and the RPC's block 0. The flag stays optional on init. |
| `link --token <id> [--agent <erc8004Id>]` | Builds the v1 statement `{tokenId, erc8004AgentId, flopDid, ss58, network, genesisHash, issuedAt}`, signs it with the FLOP key, and prints EIP-712 typed data for the seat holder to sign in their own wallet. |
| `link verify <file> [--wallet-sig <sig> --wallet <addr>] [--save] [--eth-rpc <url>]` | Checks the Ed25519 signature, that the SS58 and the DID are the same key, that `genesisHash` is the FLOP network's genesis, that the EIP-712 data matches the statement, and the wallet signature if given. With `--eth-rpc` (or `ETH_RPC_URL`) it reads `eth_chainId` and, only when that is 1, `ownerOf(tokenId)` on the seat collection. It fails unless the signer still owns the seat, so a sale kills the link. A wrong, missing, or malformed chain id fails the verify. |
| `cap set <FLOP/day> [--per-call <FLOP>]`, `cap show` | Required. No cap means `run` refuses. The day resets at 00:00 UTC. A cap, a per call cap or a `--job-budget` below 0.000001 FLOP (`MIN_CAP` in `contract/rules.json`) is refused with exit 2: a padded quote is never below that, so a smaller limit would refuse every call. One above 1000000000 FLOP (`AMOUNT_MAX`) is refused with exit 2 too: it is not a known amount. A `config.json` that holds such a cap (a hand edit) is no usable cap: `run` refuses with exit 3. So no row this tool writes records such a limit. The viewer shows a row from elsewhere that does as a red unreadable row. |
| `config set payer <holder\|requester>`, `config show` | Who a call is for. Every ledger row records it. The seat's key pays either way, so the daily cap applies to both. See "Payer assumption". |
| `run --job <id> --prompt <text> \| --prompt-file <path>` | Refuses before asking for a quote when the daily cap (or, for a requester call, the job budget) is already used up. Otherwise gets a quote, pads it, checks the caps, makes the call, and saves the response and receipt. Nothing is sent to imd. Options: `--max-tokens`, `--system`, `--provider mock\|flop`, `--live`, `--job-budget`, `--timeout-ms`, `--check-job`, `--no-link` (mock only), `--mock-scenario`. `--provider flop` requires `ETH_RPC_URL` to report chain id 1 and the live faucet and RPC genesis to equal the pinned hash, and it refuses before any quote or paid call when they do not. The mock provider does not make those calls. |
| `status [--json]` | Network, seat, address, link state, payer, today's total charged to the cap (the seat's total, all payers, `today_utc`), beside it what the gateway reported as spent today (`gateway_spent_today_utc`: the sum of the known spends) and how many sent calls of the day it reported no amount for (`gateway_spend_unknown_rows`; the text line says `<n> calls with no reported spend` when there are any). The reported total is blank (`null` with `--json`) when no call of the day has a known spend and at least one has an unknown one, so an unknown spend never shows as 0. Then `OVER CAP` on a day whose total is above its cap (`over_cap_today_utc`), and recent receipts with their `match` field, and with a `status` field when the receipt and the ledger disagree. A receipt file that cannot be read (not JSON, or not a JSON object) or matched (its seat is not a string) does not stop the overview: it is listed by name, in `unreadable_receipts` with `--json` and on one line in text output. |
| `receipt <request_id> [--refresh] [--json]` | Shows one receipt, its `match` field, and a `status` field when the receipt and the ledger disagree. `--refresh` reads the receipt again, stores it, and books what it proves. |
| `quote --prompt <text> [--provider flop]` | Free cost estimate. With `--provider flop`, it calls the gateway's free `/models/estimate`. |
| `faucet [--dry-run]` | Refuses with exit code 9, because our team doesn't use faucets. `--dry-run` prints the request it would have made. |
| `enroll [--dry-run \| --live]` | Dry run by default: prints the challenge and enroll calls it would make. `--live` does real devnet enrollment and is meant for a human on the holder's machine. |
| `session grant --owner <ss58> --days <1..10>`, `session revoke --owner <ss58>`, `session show --owner <ss58>` | Print the owner's grant or revoke as call bytes for him to sign in his own wallet, or read the session from the chain and say what room is left. They sign, send and write nothing. See "Session commands". |

Data lives in `~/.imd-flop/`, or in `$IMD_FLOP_HOME` if that's set. The ledger must be readable and writable by the user who runs the tool. Exit codes are listed below.

## Exit codes

The process exit code is the `EXIT` value in `src/errors.ts`. `src/bin.ts` assigns it to `process.exitCode`. These numbers are stable so a script can branch on them.

| Code | Name | Meaning |
|---|---|---|
| 0 | `OK` | The command finished successfully. |
| 1 | `ERROR` | A general failure. Used for a failed `init --check-genesis`, a failed `enroll --live`, a gateway HTTP error on the paid call itself (the reservation stays held, spend unknown), a ledger line that cannot be read when `status`, `cap show`, `receipt` or `receipt --refresh` reads it, or a row that cannot be placed in a total when `status` or `cap show` reads it (`receipt` and `receipt --refresh` never place a row) (the message names the line), a busy ledger when one of those commands could not read a line in flight again under the lock (`ledger lock timeout`), and any unexpected error that is not a `CliError`. A ledger lock timeout *after* the paid call also exits 1: the booking step takes the lock, and a `LedgerLockError` is not a `CliError`. An append that found the lock no longer carries its token (`ledger lock lost`, a `LedgerLockLost`) is a failed append, wherever it happens: `run` exits 1 for it, before the call as after it, except for a refusal row (exit 10). |
| 2 | `USAGE` | Bad arguments, a missing seat or key, or a value the command will not accept. |
| 3 | `REFUSED_CAP` | Refused locally, nothing sent. Used when there is no usable cap, the daily cap or the job budget is already used up (refused before the quote), the padded quote is over the per-call cap or over what is left of the daily cap or the job budget, a ledger `cap_charge` is unusable, a ledger line cannot be read or placed in a total, or a day or job total is above `AMOUNT_MAX`. The message names the line, and for a row that cannot be placed also the field. |
| 4 | `REFUSED_LINK` | The seat-to-DID link is missing or does not verify, or `--no-link` was used with a non-mock provider. |
| 5 | `REFUSED_RULE` | A section E rule (including a second key for a seat, a secret scan hit, a missing job id, or a live-run gate) or a paid-run chain/genesis refusal, at the first check and at the recheck before the child-key mint alike (`nothing sent`). The session commands use it for a wrong genesis, a runtime the encoder does not know and an active session (see "Session commands"). |
| 6 | `TIMEOUT_UNKNOWN` | The paid call timed out. Spend is recorded as unknown and is not retried. |
| 7 | `ESTIMATE_FAILED` | The cost estimate failed or returned no usable cost. Nothing was sent. |
| 8 | `VERIFY_FAILED` | `link verify` found a bad signature, a mismatch, or a failed owner check. |
| 9 | `FAUCET_REFUSED` | `faucet` without `--dry-run` always refuses (team rule). `--dry-run` exits 0 and does not send. |
| 10 | `REFUSED_LOCK` | The ledger lock could not be taken *before* the paid call (`LedgerLockError`, a lock timeout), at the cap check, or at the early check when a line in flight had to be read again under the lock. Also a refusal whose `refused_local` row could not be written for a lock error (a lock timeout, or `ledger lock lost`): the run still refuses, and the message says the refusal row could not be written and why. Nothing was sent. This code is not shared with cap refusals (3) or a broken link (4). |
| 11 | `NOT_SENT` | The provider failed before the paid request was sent: the child-key mint failed (transport error, HTTP error, unparsable body) or the run was aborted before send. The paid request never left this process, so its reservation is released: the latest ledger line is `refused_local` with cap charge 0. If another process booked a trusted receipt read for the request meanwhile, that booking stays and so does its reservation. If a trusted read later shows the gateway holds the request, the reservation comes back (see "The hold floor"). A refusal by the chain-id and genesis gate is not this code: it exits 5. |

Lock-timeout rule: if the ledger lock cannot be taken before the paid call, the CLI exits 10 and nothing is sent. If the lock cannot be taken after the paid call, while booking what the call brought back (its receipt read, or a timeout, a gateway error or a pre send failure), the CLI exits 1. Nothing was appended, so the latest row stays and keeps the reservation: the `sent` row written before the call, unless another process booked the request meanwhile. After a completed call the answer is not printed: it is in the response file, and the receipt read is in the receipt file. A later `receipt <id> --refresh` books the read. The cost the completion reported is not lost: when the ledger row records no cost, the booking step takes `usage.cost_flop` from the response file, so the refresh charges at least that cost and records it in `cost_reported`. The same holds when the append itself fails. For `receipt --refresh` a booking that cannot be written is not an error exit: it stores the read, books nothing and exits 0. When the ledger lock could not be taken it prints `ledger busy; the receipt read was stored and nothing was booked` on stderr, with the lock error in brackets. A busy ledger is not a disagreement. When the step failed for any other reason, a failed append for one, it prints `receipt and ledger disagree; reservation held, chain-final green blocked`. A damaged ledger is not a disagreement. When a ledger line cannot be read by the ledger text contract (`contract/README.md`: lines end at `\n` only, and a line that is not blank must be one JSON object in `JSON.parse`'s grammar, nested at most 32 levels), the refresh still stores the read, books nothing and exits 1, and stderr names the line: `ledger line <n> cannot be read: ...`. It prints no disagree line. The same line stops `status` and `receipt <id>` with exit 1 and the same message, and `run` refuses with exit 3 before the estimate, nothing sent. A refresh needs the stored receipt file to know what to read when the ledger cannot be read: without one it exits 1 and stores nothing. A line can also look damaged only because another process is still appending it under the ledger lock. So a command that reads the ledger outside the lock and meets a line it cannot parse first takes the lock and reads again (`src/ledger.ts`, `ledgerLines`), and names the line only when it is still unreadable there. If the lock cannot be taken within its timeout the ledger is busy, not damaged: `run` exits 10 before the estimate, nothing sent; `receipt --refresh` of a stored receipt stores its read and prints the busy line above; `status`, `cap show` and `receipt <id>` exit 1 with `ledger lock timeout`. None of them names a line. A home this reader may read but not write (or a read only file system) cannot hold the lock at all: then the reader reads without it, and a line that does not parse is named with one more sentence, `The ledger could not be locked, so this line may be one still being written.` A command that has to write, `run` for one, cannot work there and exits 1 saying the ledger could not be locked, nothing sent. The lock is one file, `ledger.jsonl.lock`, that holds its owner: a pid, a host name and a random token (`src/lock.ts`). A token is 1 to 64 characters of letters, digits, `_` and `-` (this tool writes 32 hex digits). The token read from a lock goes into the name of the reclaim right file, so a lock whose token is anything else, a path for one, is a lock with no readable owner: nothing is created or removed for it. It is created with its owner already in it (written to a temporary file that is then linked into place), so this tool never leaves an empty lock behind, even for an instant. Release removes the lock only if it still carries the holder's token. Nothing ever renames or moves the lock. A waiter removes it only when its owner is provably dead: the same host name and a pid that is gone, or this process's own pid with a token this process does not hold now (an earlier process had that pid). Age plays no part: a provably dead owner's lock is removed at once. First the waiter must hold the reclaim right for that exact token, the file `ledger.jsonl.lock.reclaim.<token>.<n>`, created the same exclusive way. If that file exists and its owner is alive or cannot be read, the waiter has no right and waits. If its owner is provably dead, the right passes to the next level. Under the right the waiter reads the lock again and removes it only if it still carries that token. Then it removes its own right file. If this user may not remove the lock (EPERM or EACCES, for one a dead holder's file in another user's sticky directory), the waiter removes its own right file and waits. Any other error at that unlink is a lock error that names the file and the code. Right after taking the lock, the holder removes every right file whose token is not its own, and every temporary file of a process that is provably dead. Every ledger append checks, right before it writes, that the lock still carries this process's token. If it does not, the append refuses with `ledger lock lost` (a `LedgerLockLost`) and writes nothing. That is a failed append, not a busy ledger: `receipt --refresh` prints the disagree line for it. The tool never removes a lock whose owner is alive, a lock owned by another host, or a lock with no readable owner. Only ENOENT means there is no lock. A lock path that cannot be read, or that is not a regular file (a symbolic link, a directory), is a lock with no readable owner. This reverses an older rule: a lock with no readable owner was reclaimed once it was older than 30 s. This version never creates such a lock, so one is a leftover of an older version or damage, and the tool fails closed. A waiter tries again at once only right after it removed a dead holder's lock itself. Otherwise it waits 25 ms before it tries again. It gives up after 5 s, whatever is at the lock path. Every lock timeout names the lock file, its age, the recorded owner and the way back: `ledger lock timeout: <path> (<n> s old) is held by pid <pid> on host <host>. If no imd-flop process is using this home any more, remove that file and run again.` The host name is text read from the lock file, so the message shows it as outside text, like every value this tool did not write: a control character becomes a space, a key shaped run withholds it, and it is cut at 255 characters. For a lock with no readable owner it says `has no readable owner` in place of the owner, and what is at the path when that is the reason (`it is a symbolic link`, `it cannot be read (EACCES)`). When the owner is gone it says so, and names what is in the way: a reclaim right file and its owner, or that this user cannot remove the lock, with the code and the file's OS owner. Removing the lock file is always the way back: the next holder sweeps the right files. Release never fails a command whose work is done. If it cannot remove its own lock, it writes one line on stderr that names the file and the code, and a waiter that may remove the lock reclaims it once this process has ended. What can be left behind: that lock; an empty temporary file `ledger.jsonl.lock.<pid>.<hex>.tmp` from a process killed between creating it and writing its owner (a known defect: the review measured about one per 600 kills, and a SIGKILL stress run of this branch left 10 in 2880 kills at random moments; it is never read as a lock and no rule removes it); and a right file whose own removal was refused, until the next holder sweeps it. Known and kept as they are: one home under two spellings in one process is not re-entrant, so the second take waits and times out (the safe way); and a holder that has exited but not yet been reaped (a zombie) counts as alive until it is reaped. The lock is tested on Linux only. Exit 3 stays cap refusals only. Exit 4 stays a broken link. Codes 0 to 11 are the only values the CLI returns.

Sent or not sent: exit 11 always means the paid request never left this process, so the call can be made again. Exit 1 does not say that. On `run` it is used when the gateway answered the paid call with an HTTP error, and for unexpected errors. Exit 6 means the gateway did not answer in time. After an HTTP error or a timeout the spend is unknown and the reservation stays held.

Known gap: if the estimate step fails, or the run is refused before the estimate, while another process holds the ledger lock, the CLI exits 1, not 10. Exit 10 covers only a lock that could not be taken before the paid call.

## Mocked vs live

The providers live in `src/providers/`. One table (`kinds.ts`), frozen when it loads, holds every provider name with its kind: whether a call is paid, whether it is the mock, and whether its link needs the seat wallet's signature. The names are `mock` and `flop`, the list in `contract/rules.json` `LEDGER_PROVIDERS`, and the ledger takes its list from the same table. The run path, the CLI and the receipt refresh ask the table by a provider's name and never compare a name themselves: the paid network gate runs for a paid kind, the wallet link and `ownerOf` check for a kind that needs it, and only the mock may use `--no-link`. A run reads its provider's name once, at its start, and uses that one value throughout. A name that is not in the table is not paid, not the mock and needs no wallet link; `run` and `receipt --refresh` refuse it with exit 2, and `quote` uses the mock for it. The run path itself also refuses a provider object of such a name, with the same exit 2 and the same text, before the link check, the gate, the estimate and any ledger row. One function (`make.ts`) makes a provider from a name, for `run`, `receipt --refresh` and `quote`. The mock is `mock.ts`, the gateway provider `gateway.ts`, and `src/gateway.ts` stays the gateway's HTTP client. `test/provider-table.test.ts` holds these rules.

- **Mocked (default):** `run`, receipts and `status` use a local stub shaped like OpenAI's API. It returns
  fixed output, a fake `request_id` and a fake receipt. `--mock-scenario` can simulate a timeout,
  a settled receipt, `key_expired`, or a failed estimate. Mock spend is tracked separately and never counts
  against the real FLOP cap.
- **Live, free, opt-in:** `quote --provider flop` (estimate), `init --check-genesis`, and `run --check-job` (public `GET api.imd.fun/jobs/:id`). `quote` stays a free estimate. It does not spend, and it does not run the paid-run gate.
- **Live, required before a paid flop run:** `run --provider flop` reads `eth_chainId` on `ETH_RPC_URL` and the devnet faucet `/chain` plus RPC block 0. The chain id must be 1. Both live genesis values must equal the hash pinned in `src/networks.ts`. The same check runs again inside the provider immediately before the child-key mint. A wrong chain, a reset (including the faucet and the RPC agreeing on some other hash), or an unavailable or malformed response refuses the run. There is no fallback that skips a source or trusts a prefix of the hash.
- **Live, built but never run by us:** `run --provider flop --live` (spends devnet FLOP) and `enroll --live`.
  The flop provider requires a gateway key from enrollment, a cap, and a link signed by both the FLOP key
  and the seat wallet. Each call mints a single-use child key capped at the padded quote and also sends
  `max_cost_flop`. Enrollment is unchanged and is not a paid inference call.
- Every request uses the User-Agent `uxp-labs-imd-flop/0 (+https://github.com/uxp-labs)`.

## Rules enforced in code (proposal section E)

1. **Keys stay local.** The seat key file is mode 600 and is never printed. Before anything is written to the ledger, a receipt, a link, a response or the config, a scan rejects anything that looks like a key: loaded secrets in any encoding, bearer tokens, `flop_ek_…` tokens, PEM keys, any 64-hex value outside a short list of known public hash fields, and fields with secret names. Public keys are only written as SS58 or `did:key`. What the Ethereum RPC server or its transport says is never shown, in any sink: a failure there is reported as a kind and numbers only (the transport error's name from a short list, the HTTP status, the JSON-RPC error code). A message built from what another server or the transport said (the faucet, the FLOP RPC, the child key mint, and a provider failure before send) quotes that text only through one function (`src/secrets.ts`, `outsideText`): the secret scan runs on the text as it came and withholds it all on a hit, known marks of at least 8 characters replace what they stand for (a part of the RPC URL shorter than 8 characters is not hidden), each `0x` and 64 hex value becomes `[hash]`, a text the scan still flags is withheld, and the text is cut to a bound. The ledger row and stderr get the same result. A message about a ledger row that cannot be placed names the line and the field, and quotes the value only when it is a string of at most 32 characters that the scan passes (`outsideValue`). Otherwise it gives the type and the length, for example `day a string of 64 characters`, so the refusal row can always be written.
2. **One DID per seat.** A seat has one spelling: a tokenId in decimal with no leading zero (`0` alone is allowed) of at most 63 digits, or `unassigned` (`SEAT_ID` in `contract/rules.json`). Any other spelling is refused with exit 2, and the message says whether the seat came from the command line or from `config.json`. For leading zeros it shows the one to use (`write 42, not 042`). A seat of 64 digits or more is refused because a number that long cannot be told from a key by the secret scan. So `042` is never a second seat beside `42`. `init` refuses a second key for a seat. Rotating writes a revocation signed by the old key and retires the old link. A receipt made under a revoked or rotated DID shows `match=mismatch`.
3. **No faucet.** `faucet` refuses.
4. **Real work only.** `run` requires `--job`. `--check-job` checks that the job exists on imd.
5. **A broken link means no route.** `run` refuses unless the link verifies, the DID is the seat's current one and the DID hasn't been revoked. `--provider flop` also requires the wallet signature, `eth_chainId` 1, and a passing `ownerOf` check through `ETH_RPC_URL`. `ownerOf` is sent only after the chain id matches. The same run requires the faucet and the RPC block 0 to equal the pinned genesis. Without an RPC, or if a read fails or disagrees, it refuses before any quote or paid call. `--no-link` works only with the mock and labels its output as bypassed.

What the cap promises. The promise is that the daily cap and the job budget are never passed without the past admitted line (`booked past what the cap admitted; the day may end over its cap`). It holds for a ledger that only this tool writes, and for a gateway that enforces the child key's cap. A ledger that was edited, moved, removed or damaged is outside the promise: the tool fails closed where it can see the damage, names the line, and prints that line where it can see a charge rise, and that is all it claims. Crashes of this tool itself, a torn line or a dead lock holder, are inside the promise. The ledger lock trusts that two processes that report the same host name share one process table. A home shared by machines or containers that report the same host name and have separate process tables is outside the promise. Within one process the lock is taken on its main thread only: a take from a worker thread is refused. (`contract/rules.json` `CAP_PROMISE`.)

Spend-guard rules, ported from `spend-guard/`:
- The quote is padded by 20 tokens for the Qwen chat template. On a paid flop run, the chain-id and genesis checks come before that quote. If the estimate fails, or returns no usable cost (a cost that is not a finite number above 0, or a token count that is negative or not a finite number), nothing is sent.
- A body a server sent that holds a number that is not finite (1e999 and -1e999 parse to Infinity, and JSON would write that back as null, which means unknown here) is not JSON this tool reads. It takes exactly the path of a body that is not JSON at that place, with the fixed reason `non_finite_number`, the word spend-guard prints, and never a quote of the body or the number. So an estimate like that fails (`estimate failed (non_finite_number)`, exit 7) and nothing is sent, a child key mint answer like that is a pre send failure (exit 11), an Ethereum RPC, faucet or FLOP RPC answer like that fails the paid run gate (exit 4 or 5), and an enroll challenge or enroll answer like that enrolls nothing (exit 1). The paid call's answer and the receipt read are parsed by `@flop-labs/client`, and they follow the same rule: a 200 answer of the paid call like that leaves the spend unknown and the reservation held (`timeout_unknown`, exit 6, reason `FlopValidationError: no answer; spend unknown, not retried (non_finite_number)`), an HTTP error answer stays that gateway error (`HTTP 500 (non_finite_number)`), and a receipt read like that is not a trusted read, books nothing, and the stored receipt records `Gateway response is not valid JSON (non_finite_number)` (or `non_finite_number` for an HTTP error answer, so a 401 sets no flag). Nothing is stored with null in place of a number the gateway sent. One check decides this everywhere (`src/outside-json.ts`): `readOutsideJson` reads every body and frame `src/gateway.ts` parses, and `nonFiniteSeam` is the fetch `src/providers/gateway.ts` gives the client for those two calls. That fetch sends first, reads the body text once from a clone, and when the body holds such a number hands the client a new answer with the same status and headers and the body `non_finite_number`, which is not JSON, so the client takes its own path for a body that is not JSON. It never throws because of what a body holds. Every other body, and one whose read fails, reaches the client as it came. Neither reader applies a depth limit to server bodies or recurses, and neither bounds a body's size (the client did not either).
- A refusal that needs no quote comes before the estimate, so the prompt is not posted for nothing: the daily cap (every payer) or the job budget (requester) is already used up, a ledger `cap_charge` is unusable, or a ledger row cannot be placed in a total. The ledger row is the usual `refused_local` with a null quote. The cap check under the ledger lock still runs after the quote and stays the authority.
- If the pre-mint chain-id or genesis recheck fails (exit 5), or the child-key mint fails or the run is aborted before send (exit 11), the latest ledger line is `refused_local` with cap charge 0. Status does not list that attempt as pending. The earlier `sent` line is the crash marker written before the call; the latest line is the one the cap uses. A crash between those two lines can leave `sent` as the latest line. If another process booked a receipt read for the request meanwhile, that booking stays (see the failed call rule below).
- A call is refused locally if it's over the per-call cap or what's left of the daily cap. The daily total is every call of the seat that UTC day, whoever the call was for. A requester call must also fit what's left of its job budget. Every amount this tool compares is at most 1e9 FLOP (`AMOUNT_MAX`). An amount is on the 6 decimal grid when `floor(x * 1e6 + 0.5) / 1e6` gives back the same number, and then its count of millionths of a FLOP is exact. The total already charged is the exact sum of those counts, never a float sum. A total above `AMOUNT_MAX` is not a known amount: `run` refuses with exit 3, nothing sent, and `status` and `cap show` exit 1, both saying the total is above the largest amount this tool compares. The cap check is made in the same integers: a call is over when its padded quote in millionths is above the cap less the total. So for amounts on the grid every total and every cap decision is exact. Only an amount off the grid is rounded, a charge up to the next millionth and a cap or budget down, so rounding never admits a call over the cap. This is residual R-g in `contract/rules.json`, and it closes when money moves to exact base units (money stage 2). `status` and `cap show` print the total.
- A ledger row that cannot be placed fails closed, as an unusable charge does (`src/ledger.ts`, `placed`). The daily total counts the latest row of each request whose `day`, `seat` and `provider` are this seat's, this provider and this UTC day. The job total counts the latest row of each request whose `job`, `provider` and `payer` are this job, this provider and `requester`. A row that would count toward a total if one of those fields were readable, and whose value there is not usable, refuses the next call: exit 3, nothing sent. The message names the ledger line, so the holder can repair or remove it. A usable day is a UTC calendar date written `YYYY-MM-DD` from year 0001 on, a usable seat is a canonical tokenId (decimal, no leading zero, at most 63 digits) or `unassigned`, a usable provider is `mock` or `flop`, a usable job is 1 to 120 printable characters with no space, and a usable payer is `holder` or `requester`. A row with a usable value that is not this total's (another seat, say) is not this total's, whatever else is damaged. Only the latest row of a request is placed: an older row of the same request is superseded, so damage there loses no charge and refuses nothing. A line with no usable request id (1 to 128 printable characters, no space) cannot be superseded and cannot be placed: unless it is a refusal written before a request id exists (`refused_local`, cap charge 0), it refuses the next call and names the line. So when the damage is to the latest row's request id, that row refuses rather than let an older row of the request stand in for it. `status` and `cap show` read the same totals, so they exit 1 with the same message. The viewer flags such a row `ledger row cannot be placed in a total` and never shows it as fine (`contract/vectors/ledger-placement.json`).
- The hold floor. Every paid call mints a single use child key at the gateway capped at the call's padded quote, so the padded quote is what the call was allowed to spend. From the moment a call is sent, its cap charge is never below that padded quote. A gateway read (settled or released, with any amount or none) and a reported cost can only raise it. The `spend` field still records what the gateway says was spent. So the daily cap and the job budget count what each call was allowed to spend, not what it ended up costing. The reason: a gateway read is not final, since per the gateway's OpenAPI (CredentialReceipt), read 2026-11-11, later reconciliation can change what a receipt shows, and the child key's cap is the one bound the gateway enforces. The floor lifts only when the call's settlement is proven on chain, and nothing in imd-flop proves that yet. The one release is "nothing was sent" (see the failed call rule below). Rows that an older version booked below their hold are not migrated: they keep their charge, and a later read only raises it. Such a raise passes what the cap admitted and says so (see the next rule).
- A booking that puts the day in a state the cap did not admit prints `booked past what the cap admitted; the day may end over its cap` on stderr and records it in the row's `reason`. The rule: what the cap admitted for a request is its known booked charge, which every later admission counted, or, when that charge is not a known amount, its padded quote, the charge the call was sent with. A booking above that passes what the cap admitted. That covers a released hold that comes back (from 0), a charge raised above the call's padded quote (a settled amount or a reported cost above what the call was allowed to spend), a row an older version booked below its hold that a later read raises back toward it, and a repair of a damaged charge above the padded quote. A repair to exactly the padded quote says nothing. Writing `run`'s `sent` row again, after the ledger lost the request's row during the call, is such a booking too: calls admitted meanwhile did not count it. Once a request was booked past what the cap admitted, every later row of it keeps the line first in its `reason` (`src/booking.ts` is the one place that carries it), so the mark is not lost on the next booking. `status` marks today's total only: `over_cap_today_utc` and `OVER CAP` are about the current UTC day. A hold that comes back on an earlier day is shown by its row, whose `reason` carries the past admitted line, and by the viewer, which flags that row and never shows it green.
- A timeout is never retried. Its spend is recorded as `null` with its `request_id`. For the cap, unknown spend counts as the padded quote. If another process already booked a settlement for the request, that row stays and the timeout is not written over it.
- Receipts are labeled `gateway observed` and `chain_final=false`, because nothing verifies chain settlement yet. An amount on a receipt (reserved or settled), and any float amount on a ledger row, counts only when it is a finite number that is not negative and not above 1000000000 (1e9 FLOP, `AMOUNT_MAX` in `contract/rules.json`). Up to there the 6 decimal grid survives the float, and above about 2^33 FLOP a double cannot hold it at all. Anything else is unknown and shows blank, never 0. A total of such amounts never adds an unknown one as 0: `status` counts those calls apart (`gateway_spend_unknown_rows`). Exact amounts in base units are digit strings and have their own rule (see "Exact amounts"). A 401 `api_key_expired` gets its own `key_expired` flag.
- What a receipt says, per the gateway's OpenAPI (CredentialReceipt), read 2026-11-11. The states `reserved` (quota held, no completion checkpoint) and `estimated` (reservation kept after completion, no reconciled spend) are unresolved. `settled` (spend reconciled) and `released` (reservation returned to quota) are terminal ledger states. `settled_spend` is a number or null from the gateway's legacy floating point ledger, and null means unknown, including for a released reservation. `settled_spend_raw` is the exact amount as a decimal digit string of base units (10^18 per FLOP), and null means unavailable, never an inferred zero. The receipt file keeps it as it arrived, the ledger row records it as `spend_raw`, and the ledger `spend` records `settled_spend` (see "Exact amounts"). Neither lowers the cap charge (see "The hold floor"). `channel_id` is the compute channel the request was served on. `terminal_event` is a channel event id that may cover several requests. It is not a payment hash for one request, so it is not proof that this call settled.
- A receipt read settles an attempt only when it is an HTTP 200 answer for this request id and its stored copy needed no redaction by the secret scan. Any other read keeps the reservation. Such a read moves the ledger state only to one of the four gateway states (`reserved`, `estimated`, `settled`, `released`): a read in any other state, `refused_local` or `sent` for example, counts as a read with no state, so a gateway answer never sets a local state. `run` and `receipt --refresh` put every read through one decision (`src/settlement.ts`, `decideBooking`).
- One booking step. Every ledger row written for a request after its paid call goes through `src/booking.ts`: `run`'s own receipt read, what `run` saw when the call itself failed, and `receipt --refresh`. Under the ledger lock it reads the latest ledger row of the request, decides, and appends one row when something it records changes. In real use one seat has several processes at once: workers running jobs, and something refreshing open receipts. Two of them can read the same request, and the spec says later reconciliation can change the gateway's ledger observation, so their reads can differ. That is normal, not an attack. Each one decides against what the other already booked, and two trusted reads book the same spend and charge whichever comes first. The network read and the receipt file write happen before the lock is taken. If the ledger no longer holds the request's row when `run` comes to book (the file was moved or removed during the call), the booking step writes `run`'s `sent` row again under the same lock and books against it, so the paid call stays on the books. That row says it was booked past what the cap admitted, and `run` prints the line. `run` appends no ledger row of its own after the paid call.
- A booked settlement is never lowered by a later read. An equal amount may still move the state, and a higher amount is booked. The state only moves forward: a pending read never takes a settled or released row back. A read that would lower a booked settlement is not booked, and `run` and `receipt --refresh` print `receipt and ledger disagree; reservation held, chain-final green blocked` on stderr. A ledger charge that is not a known amount is never replaced by a guess either: unless the read proves a settlement and the row records a known padded quote, which the charge then is (or the settlement, when higher), the same line is printed and the booking stays as it is.
- A failed call is a report, not a receipt read (`src/settlement.ts`, `decideFailure`). When the paid call times out, gets a gateway HTTP error, or fails before anything was sent, `run` books that through the same step, against the latest row of the request. A timeout or a gateway error moves a row that does not settle to `timeout_unknown` or `error`, and its charge stays. "Nothing was sent" is a local fact: the paid request never left the process. It releases the reservation: `refused_local`, cap charge 0, but only from a row still in state `sent` that no trusted read has reached. Any fresh read for this request id (HTTP 200 with a receipt whose request id is ours) shows the gateway knows the request, whatever its state field says, a receipt with no state included, and even when its stored copy had to be redacted. It beats a "nothing was sent" report in both orders. A read stored redacted still proves no settlement and moves no state: it only keeps or brings back the hold. If the read was booked first, the report does not release the row: a reserved or estimated row says so by its state, and a sent row the read left in state `sent` (a receipt with no state) is marked `receipt_seen`. If the report was booked first, a later trusted read brings the reservation back, its padded quote, raised by a settled amount or a reported cost as any hold is. A receipt with no state takes the row back to `sent` and moves it no further. The day can then end over its cap, because another call may have used the freed room, and the booking says so (see "The hold floor"). When that padded quote is not a known amount the hold is unknown, so nothing is guessed and the read disagrees. A report never replaces a booked settlement: if another process refreshed the request and booked a settled or released row while the call ran, that booking stays. A charge that is not a known amount is left as it is. A report that is not booked is still recorded: one row keeps state, spend and charge exactly and records the report in `reason` (for example `timeout reported; booked settlement kept`) and `http`. `run` still exits with its own code for what it saw, and its message says what the ledger kept. When the ledger holds a settlement for the request the message says so and does not call the spend unknown.
- A gateway read alone never lowers a booking. On FLOP a refund comes from an upheld fraud verdict: per FLOP's docs a session's payment sits in escrow against the proof, and an upheld fraud verdict refunds the agent. That refund is a chain event, and nothing in imd-flop verifies the chain yet. When it does, a chain proven refund is the one thing that may lower a booking, and a settlement proven on chain is the one thing that may lift the hold floor. `decideBooking` marks the one place where that will plug in.
- The cost a completion reports (`usage.cost_flop`) may raise the cap charge and never lower it, before and after settlement. It counts only when it is a known amount, by the same rule as every amount (finite, not negative, not above `AMOUNT_MAX`). Any other reported cost is unknown: it raises nothing and is not recorded. A settled call is charged the highest of its padded quote, its settled spend and that cost. When that cost is above the padded quote and the settled spend, so the charge is that cost, the ledger `reason` reads `cap charge raised to reported cost`. A cost at or below the padded quote raises nothing, and the reason does not say it did. The `spend` field stays the settled figure. A settled row that was booked before this rule with a cap charge below its reported cost is raised to that cost by the next `receipt --refresh` for it, whatever that refresh reads. The refresh appends a new line, and the old line stays in the ledger.
- Whether a stored receipt and the ledger disagree is worked out from the two files each time it is shown, never stored (`src/settlement.ts`, `reconcile`). It is the decision the viewer makes for the same files, pinned for both by `contract/vectors/reconcile.json`. `run`, `receipt <id>` and `status` show the receipt with `status=receipt and ledger disagree; reservation held, chain-final green blocked` (a `status` field with `--json`) when one of these holds. A settled or released receipt has no settled or released ledger row with the same spend, and an amount on one side only counts as different. A receipt in any other state sits beside a settled or released row, or says it is chain final. The row's call timed out or got a gateway error, and no read has been booked for it since. The receipt file holds the last read written to it, merged with what it held before (a failed read keeps the gateway fields it held). Each read is written before the ledger lock is taken, and the write is not under the lock. So when two refreshes of one request run at once, the file holds whichever read was written last, which need not be the later read. The ledger is not affected: each booking is decided under the lock against the latest row. After a read that was not booked because it would lower a settlement, the file holds the lower amount, the ledger keeps the booked one, and the status says so until a later read agrees. A failed read is not compared, and neither is a receipt whose identity does not match the row by the viewer's rule: the request id, job, seat and DID must each be a non-empty string on both sides, and equal. The cap charge is not compared.
- The `match` field compares identity fields only: the request id, job, seat and DID. It does not compare amounts or state: that is the `status` field. It's `matches` only when those fields equal the ledger row, the seat and DID also equal the seat's current link, and that link verifies. Otherwise it's `mismatch`, listing the fields that disagree, or `pending` if there's no receipt yet.

## Exact amounts (money stage 1)

Per FLOP's own sources, read 2026-11-11: the chain counts money in whole base units, 10^18 per FLOP, in a u128. Its spec forbids floating point conversion in encoders, and its official test vectors carry money as decimal digit strings. The gateway receipt carries `reserved_spend` and `settled_spend` as numbers from a legacy floating point ledger, and `settled_spend_raw` as the exact amount.

- An exact amount is a string of the digits 0 to 9 only, whose value is below 2^128. It is kept in canonical form: no leading zeros, `0` for zero. Anything else is unknown, never 0 (`src/amount.ts`, `exactAmount`). The viewer has the same rule, and both run `contract/vectors/exact-amount.json`.
- `spend_raw` on a ledger row is the exact spend in base units as a canonical digit string, or null for unknown. A row written before this stage has no `spend_raw`, and that is unknown too. It is decided with the rest of the booking (`decideBooking`). Only a trusted read in a settled or released state brings an exact amount. The exact amount describes the booked float spend, so the two are set as a pair, by the read that books the float spend. When a read books a float spend the row did not hold (the row's was unknown, or a different known amount), the exact amount is that read's own, or unknown if it has none. A read whose float amount is unknown never sets or changes the exact amount beside a known float spend. Otherwise (the same float spend again, or no float spend on either side) it only rises: an unknown one is filled, a higher one is booked, and a lower or equal one changes nothing. A read that is not booked sets nothing. So two trusted reads book the same pair in either order: `test/decision-properties.test.ts` walks every pair of them over its grid and finds no exception. An exact amount that arrives on a later read appends one row.
- A receipt read that fails keeps every field the stored receipt took from the gateway: `request_id`, `correlation_id`, `state`, `reserved`, `settled`, `settled_raw`, `terminal_event` and `channel_id`, and `chain_final`. This holds for `run`'s own read and for `receipt --refresh` alike: one function decides what a receipt file holds after a read (`src/receipt-store.ts`, `storeRead`). It reads the stored file just before it writes, so a read that `run` makes after another process stored a settled receipt keeps that receipt's fields when it fails. A failed read also stores `last_known_at`, the time those fields were last read: after several failed reads in a row it still names the last good read. A fresh read drops it.
- The receipt file keeps `settled_raw` exactly as the gateway sent it. It is not checked before it is written, so the secret scan sees what arrived.
- `channel_id` on a stored receipt is the gateway's channel id when it is a non empty string of at most 128 printable characters with no space, else null. Proof on chain is per channel: a receipt is later tied to the channel's finalized events through this id. Nothing decides on it yet. `receipt <id>` and every receipt line print it when present.
- The cap still runs on the float figures. No cap, quote, charge or settlement decision reads `spend_raw`, and the float and exact figures are not compared yet: the right tolerance needs a live receipt.
- The rule for what comes next: all money math moves to base units before any real value moves through this tool.

## Payer assumption

The seat's daily cap bounds every call the seat's key pays for, whoever the call is for.
Today the gateway has no way for a third party to pay. So the seat's key pays for every call, and every call counts against the seat's daily cap.

- `holder` (the default): a call must fit the per-call cap and the seat's daily cap.
- `requester`: the call is for an imd requester's job. This is a label on the ledger row plus a second, narrower limit. Each `run` needs `--job-budget <FLOP>`, which caps the total requester spend on that job. A requester call must fit the per-call cap, the seat's daily cap and the job budget. A limit with nothing left refuses first, before any quote: the daily cap, then the job budget. Then the padded quote is checked against the per-call cap, the daily cap and the job budget, in that order. The refusal names the first check that fails.

The job budget is supplied by the caller for each job id. It never replaces the daily cap, which the holder sets.

`status` and `cap show` report today's spend as the seat's total, all payers.

Each ledger row records two running totals. `spent_before` is the seat's spend today before the call, for every payer. `job_spent_before` is the job's requester spend before the call, and `null` on a holder row. Rows written before this rule have no `job_spent_before`. On those requester rows `spent_before` was the job's spend. The viewer works out their job budget left from it and shows their daily cap as not checked, so such a row never gets the green chain final chip.

Not built: when FLOP ships proxies or escrow pools and a call is funded by another account, that call will be bounded by that account's limit and will not count against the seat's cap.

## Session commands

A seat spends on FLOP through a session. The owner S of the seat grants the seat's device key D a session with caps. Three keys, three places: S is the owner's own wallet, and this tool never holds it or asks for it; D is the seat's device key, which this tool holds; C is a channel key made fresh for each run. The code is `src/session/`.

What each command prints, to stdout only, in words or with `--json`:
- `session grant --owner <ss58> --days <n>`: the seat, the network, S and D as SS58, the head it read at; the call `FlopSessionKeys.create_session` as 0x hex; the blake2b 256 of the call's bytes; the encoder's own words for those bytes (`describeOwnerCall`), unchanged; one sentence of what the grant allows in all; a last line that the owner signs it with his own wallet.
- `session revoke --owner <ss58>`: the same for `FlopSessionKeys.revoke_session`, and one line of what is stored for the pair, by one function that `grant` also uses to decide: `no session`, `an active session`, `a session past its expiry` (stored as active, with the head at or past `expires_at`), or `a revoked session`. The same name is in the JSON as `stored`. It prints the call in each case.
- `session show --owner <ss58>`: the head (number and hash) and the runtime; whether the runtime is in the encoder's table, with its two constants and the era period; the session as stored, each amount in raw and in FLOP, or `no session`; the session nonce, with `(not stored: the chain's default)` when the chain holds none; the breaker, or `none`; the seat's local caps; the notes below; and the room for one call.

The caps of a grant come from the seat's own local caps, exactly:
- `per_tx_limit` is the seat's per call cap, `daily_cap` its daily cap, `spending_cap` the daily cap times `--days`, and `duration_blocks` the runtime's `SessionEpochLength` times `--days`.
- A raw amount is the cap's count of millionths times 10^12. Nothing else: a cap off the 6 decimal grid has no exact raw amount and refuses.
- `--days` is required, a whole number from 1 to 10, with no default. A day of `--days` is one epoch of the chain's daily cap: 86400 blocks at 1014020, from the runtime's table, not typed. The tool holds no block time, so it says blocks and epochs, never hours. The local daily cap is per UTC day; the chain's is per epoch.
- The allow list is always exactly `ComputeChannel`: the encoder writes no other.
- A cap is stored by `cap set` as the nearest number of its text. A text with more digits than a number holds (for example `0.99999999999999999`) is stored as the number nearest to it, so its own amount is lost before the grant. This is the contract's open question Q-AMOUNT-TEXT (`contract/rules.json`), shared by the three tools and not fixed here. The grant follows the stored cap exactly and prints each amount in raw and in FLOP, so the owner reads what is granted.
- `--days` is also checked against the runtime read: `SessionEpochLength` times the days must not be above `MaxSessionDuration`. Above it, `grant` refuses with exit 5 and names the days asked, the most whole days that runtime allows, and both constants in blocks.

The room for one call is the least of `per_tx_limit`, `daily_cap` less `epoch_spent`, and `spending_cap` less `spent`, never below 0. It is `none`, with every reason that applies, when no session is stored, the session is not active, the head plus the encoder's era period of 64 blocks reaches `expires_at` (a call signed now may land up to that many blocks later), the allow list is neither empty nor holds `ComputeChannel` in any case of letters, or the breaker is tripped. It is unknown, with the reasons, when the runtime is not one the encoder knows, or when a value it needs is unknown and no known value already rules a call out. An empty allow list allows every pallet: the room is computed, and a note says it is not a grant this tool writes.

A known room does not count the breaker's limits per period: the chain's `CircuitBreakerMaxSpend` and `CircuitBreakerMaxTxs` per `CircuitBreakerPeriod`. This tool does not hold them, so the room line ends with a clause that says so, and the JSON room carries the same text as `not_counted`. A room of none or unknown does not carry it. The room is as of the finalized head it names: spends after that head are not in it.

The notes of `show`: a chain cap above its local cap; an allow list that is not exactly `ComputeChannel`; and, when the head is at or past `epoch_start` plus the epoch length, that the chain resets the epoch's spend at the next call, by the lab's reading of the runtime (inferred), so the room shown is a lower bound.

What each reads:
- The seat as the other commands find it, its local caps from `config.json`, and D from the seat's `identity.json` (its did:key).
- The chain through `src/chain-read` only: first the hash at height 0, then `readSessionState` at the finalized head. One transport: the network's rpc, or the one the caller of `main` hands in (tests always do).

What they never do: read a key file or call `loadSigner`; sign or send anything; write any file; store the owner.

Unknown is never 0. In words it is `unknown (<reason>)`; in JSON a value of `null` with a `reason` beside it. Amounts in JSON are decimal strings of raw units.

Refusals and exit codes:
- 2: `--owner` missing, not SS58, a bad checksum, not in its canonical form (a reserved first byte, or a two byte form of a prefix below 64), another prefix than the network's, or equal to D; an option given more than once, on any command (the words name the option); `--days` missing or not 1 to 10, or given to `revoke` or `show`; a sub command that is not one of the three; no identity file for the seat. These come before any node call.
- 3, `grant` only: no usable local cap (as `run` refuses it), or a cap off the 6 decimal grid. Before any node call.
- 1: the hash at height 0 cannot be read; the read is unknown; for `grant` and `revoke` the stored session is unknown (a record of another pair is unknown); for `show` anything it shows is unknown (the session, the nonce, the breaker, the local caps or the room). An identity whose did is not a did:key is 1 too.
- 5: another hash at height 0 than the network's pinned genesis; for `grant` and `revoke`, a runtime at the head that is not in the encoder's table (the words name the spec); for `grant`, a session known and active for the pair (the chain would refuse a second one: revoke it first), or days above the runtime's longest session (`SessionEpochLength` times the days above `MaxSessionDuration`).
- 0: otherwise. `show` exits 0 with a room of none when everything it shows is known.

A stored record that is revoked, or whose `expires_at` is at or below the head, does not stop a grant: the call is printed with one line that says whether the chain takes a new grant over a stored record is not shown yet.

Not checked by this tool: the chain's most sessions per owner and per delegate (`MaxSessionsPerOwner`, `MaxSessionsPerDelegate`). A grant it prints can still fail on chain for that reason.

Not shown yet (a devnet batch of the lead's, G-19):
- a grant printed by this tool, signed by the owner and landing as `SessionCreated` with the derived caps;
- whether the chain takes a second grant for the same pair after a revoke;
- the expiry's edge: whether a call at exactly `expires_at` is taken;
- whether a holder's own wallet signs a hex call on FLOP devnet.

Today no recorded read names a runtime the encoder does not know: chain-read's key table has a line for 1014020 alone, as the encoder's table has. The tests make that case with a network whose pinned genesis is another hash.

## Chain encoder

`src/chain/extrinsic.ts` encodes and signs one kind of FLOP chain call for the planned session channel provider. No command, provider or network code uses it yet. The session commands use the owner's two calls below, the words, `runtimeIdOf` and the era period, and nothing that signs.

- What it writes: a signed version 4 extrinsic of `FlopSessionKeys.execute_via_session` around exactly one inner call of `ComputeChannel`: `open_channel`, `top_up_escrow`, `timeout`, `force_open` or `expire_force_open`. The signer is the device key's account, with an ed25519 signature. The era is always mortal with a period of 64 blocks; the result names the last block at which the transaction is valid. The tip is always 0 and the metadata hash check is off. A payload longer than 256 bytes is signed as its blake2b 256 hash.
- The declared spend is computed, never passed: the escrow of `open_channel` and `force_open`, the amount of `top_up_escrow`, 0 for `timeout` and `expire_force_open`. It is taken from the encoder's own copy of the input.
- The input is read once. Every field of the input, the inner call, the sla and the birth block, the signer's public key and sign function, and the runtime id's four names are read exactly once, checked and copied. Everything after comes from that copy, so changing the input during or after the call changes nothing the encoder writes or returns.
- Inputs are typed: 32 byte values as `Uint8Array` (taken by the array's own internal length and bytes), amounts and u64 values as `bigint` in range, u32 values as whole numbers in range, enums by name. A field must hold its value: a getter is refused.
- Four objects are read as exactly their fields: the input, the inner call, the sla and the birth block. A field missing or extra is refused.
- Two objects are read by their named own fields only: the signer by `publicKey` and `sign`, and the runtime id by its four names. Each is read once as an own value. A name the object does not have as an own field reads as undefined. So a signer made from a class with `sign` on its prototype is refused, with `the signer has no own sign function: one inherited from a class or a prototype is not read`. Other fields are allowed and never read: a signer may carry its own state, and a whole table entry is a runtime id too. `sign` is called with the caller's signer as `this`.
- In all six objects, a field that is an accessor is refused (`BAD_INPUT`), and a Proxy's get trap is not used. An input whose own code throws while it is read, such as a Proxy trap, throws that error, and nothing is signed by then.
- It reads no key and no file. It takes the public key and a sign function.
- Before the sign function is called, the call bytes are read back with the strict reader (`src/chain/reader.ts`) and compared with the copy of the input, field by field.
- Refused before the sign function is called, each with a code: a runtime not in its table, a wrong length, a value out of range, an enum name not in the table, an inner call not among the five, a field of the input, the inner call, the sla or the birth block missing or extra, a field of any of the six objects that is a getter, a spend, era or tip passed in, and call bytes that do not read back as the input.
- What can fail after the sign function is called comes only from the signer: a sign function that throws (`SIGNER_THREW`, which says only that the sign function threw: nothing of the thrown value is kept, not its text, its class or the value itself), and a signature that is not 64 bytes or does not verify over the payload (`SIGNATURE_INVALID`).
- The result's fields and words are read back from the final bytes, and the signature is verified there. The exported words functions (`src/chain/describe.ts`) take only bytes and a runtime's four names, so the words cannot differ from the bytes. No exported function takes a runtime object: a runtime is found by its four names in the frozen table, each read once as an own value. An id without one of them finds no runtime (`RUNTIME_UNKNOWN`).
- Everything `src/chain` exports is frozen where it is defined: objects and arrays at any depth, and functions and classes with their prototypes and their methods (`ByteReader`, `ChainEncodeError`). `test/chain-frozen.test.ts` walks every export.
- Its table, `src/chain/runtimes.ts`, is written by `node scripts/chain-table.mjs` from the 1014020 metadata held by the observatory recording `recording-20261112080132-05842a6db1e9c890`, picked by the sha256 in `research/2026-11-12-session-rerun-1014020/facts-1014020.json`. ## Chain reads

`src/chain-read/` reads a session's room from a FLOP node, for the channel provider to come. The session commands call `readSessionState` and `blockHash`, and nothing in it can send: it asks a node only `chain_getFinalizedHead`, `chain_getHeader`, `chain_getBlockHash`, `state_getStorage` and `state_getMetadata`, and a test fails if any other method name appears there.

- What is read. Two entry points (`read.ts`). `readSessionState(transport, owner, delegate)` reads `FlopSessionKeys.Sessions(owner, delegate)`, `SessionNonces(owner, delegate)` and `CircuitBreakers(delegate)`. `readBlockEvents(transport, { number, hash })` reads `System.Events` of one block. Each answers the block's number and hash and the runtime the door pinned beside the values.
- The block argument. `readBlockEvents` reads its block once, before the first node call, into a copy: an object with exactly the own fields `number` and `hash`, each read through its own descriptor. An accessor is refused and a Proxy's get trap is not used. Every later line uses the copy. Anything else is unknown with a reason that names what was wrong: not an object (null too), a missing field, an extra field, an accessor. A block whose own code throws while it is read is unknown with a fixed reason. It never throws and makes no node call then.
- From which block. A session is read at the finalized head, taken once: every other call is made at that one hash. The number the head's header names is checked with `chain_getBlockHash(number)` after the header and before any storage read; unless the answer is the head's hash the read is unknown, and the reason names the number and both hashes. Events are read only at a block the node reports finalized and canonical: at or below the finalized head, and `chain_getBlockHash(number)` is its hash. A block is decoded in the encoding of the runtime that executed it: its own `System.LastRuntimeUpgrade` names the runtime, and the metadata is read at its parent.
- Through the observatory's decoder only. `door.ts` is the one file that imports the observatory, and only `flop-observatory/scale/block`; `shape-file.ts` is the one file that reads a shape file, through the package. The runtime must be on the decoder's reviewed list. The pin is proven through the door before it is used: the block's `System.LastRuntimeUpgrade` bytes are decoded as a stored value with that pin (no key parts, the key from the key table), so the door checks the metadata against the reviewed line, the shape file's text and the key, and the record it decodes must name the spec `runtimeOf` named. A pin the door refuses makes the whole read unknown, for both entry points, with the door's words. The two fixed parts of each storage key come from `key-table.ts`, written by `node scripts/read-key-table.mjs` from the committed shape and the recorded metadata; the account parts are hashed with `@noble/hashes`, and the door builds each key again and refuses one that differs.
- What unknown means. Every function answers a known value or `unknown` with a reason, and nothing throws for what a node said. A node error, a timeout, a wrong shape, an answer that is not 0x and even lower case hex, an answer over its cap (`node.ts` `CAPS`, each with its reason), a refusal of the door, a field the shape does not state and a number out of range are each unknown. Unknown is never 0 and never a default. An Optional entry (`Sessions`, `CircuitBreakers`) the chain holds no value for is `absent`: known, and not unknown. A Default entry (`SessionNonces`) the chain holds no value for is the chain's own default from the metadata (0), known, with `stored: false`; never absent.
- The record asked for. A stored session record whose `owner` or `delegate` is not the account asked is unknown, whatever key it was answered under; the reason says the record names another owner or delegate.
- The cross check (`cross-check.ts`). It takes the values the two reads returned: the known state of `readSessionState` and the known events of `readBlockEvents`. It reads their fields as they are and takes no copy. A state whose known session record names another owner or delegate than the state's own is unknown, before any event is looked at. The totals of the session's `SessionCallExecuted` event at a block must equal the stored session at that block; a disagreement is unknown and names both values.
- Only the five, at run time. `READ_METHODS` (`node.ts`) is frozen, and the transport `nodeTransport` returns refuses any other method before `rpcCall` is called, so a cast puts nothing on the wire; the read turns the refusal into unknown. Nothing a transport throws or answers makes a read throw.
- Everything `src/chain-read` exports is frozen where it is defined: its tables at any depth, and its functions. `test/chain-read-frozen.test.ts` walks every export.
- One socket. `src/node-rpc.ts` `rpcCall` is the one place imd-flop opens a socket to a node; the genesis check and the reads both use it. It takes a frame as the call's answer only when the frame is an object that is not a list, its `jsonrpc` is exactly `"2.0"`, its `id` is exactly the id sent (`CALL_ID`, 1), it has no own `error` key and it has an own `result` key; the result is then the frame's `result` as it is, so null only when the node wrote null. A frame with an own `error` key, whatever its value, is a failed call: an error object with a text `message` is quoted through `server-text.ts`, any other gives "rpc error". Every other frame is a failed call whose words say it is not an answer to the call, and the frame is never quoted.
- The frame cap and the close. Each caller hands `rpcCall` its limits: a timeout and a frame cap in characters, both required whole numbers above 0, with no default. The timeout is at most `MAX_TIMEOUT_MS` (2147483647 ms, the longest delay a timer holds: a longer one would fire after 1 ms); a larger one is refused with `rpc limits refused: the rpc limits' timeoutMs must be at most 2147483647`, before any socket is made. Before anything is made of a frame, a frame that is not text ends the call with `rpc frame is not text`, and a text longer than the cap ends it with `rpc frame of N characters is over its cap of M`. Only then is it parsed. The cap stops the parse, not the receive: the engine holds the whole frame by then. A socket that closes before an answer ends the call at once with `rpc socket closed before an answer`; a close after the call has settled does nothing. The node's transport (`node.ts`) passes one cap, `FRAME_CAP_CHARS`, and a frame is capped as the node wrote it: the cap is the largest answer any read accepts (2 plus 2 times the largest of `CAPS`) plus `FRAME_WRAPPER_CHARS` (256) characters for the frame, computed from `CAPS`. The compact frame is 36 characters. A node that writes more than 256 characters around an answer of the largest size is refused with `rpc frame of N characters is over its cap of M`, and the read is unknown: a refusal, never a wrong answer. No finite cap takes every legal frame. The genesis check passes 65536 characters and 15 seconds (`GENESIS_RPC_LIMITS`). `node-rpc.ts` imports nothing from `chain-read`.
- Tests give a scripted transport that answers from the observatory's committed recordings (`test/lib/recorded-node.ts`), and no test opens a socket.

## Channel key (not used by any command yet)

`src/channel/` holds five files: the channel key C and the exact bytes it signs, for the channel provider to come. No command uses it. It opens no socket, writes no file and sends nothing.

What the modules are (the shared freeze helper is `src/freeze.ts`, below):
- `errors.ts`: the refusal codes (`WRONG_LENGTH`, `OUT_OF_RANGE`, `BAD_INPUT`, `SELF_CHECK`, `SIGN_FAILED`) and `ChannelError`, exit 5. A message names the field and the length or range. It never carries bytes or hex of an input.
- `bytes.ts`: the shared input checks of `src/plain-input.ts` bound to the channel's refuse, fixed width little endian integers, ASCII and UTF-8 text, and lower case hex.
- `transcript.ts`: the channel id, the receipt and the turn ack, as bytes. No hex, no signing.
- `auth.ts`: the request message and its five headers. No signing. The time, the nonce and the challenge are handed in.
- `key.ts`: the key itself. It is the only file under `src` that names the sr25519 library.

The layouts, each read from FLOP's SDK 0.6.0 (`dist/compute-channel/`), read and not imported. All integers are little endian.
- Channel id (`transcript.js`, `channelIdV1`): blake2b 256 of the 23 ASCII bytes `FLOP/COMPUTE_CHANNEL/ID`, the byte 1, the genesis hash, the agent, the miner (32 bytes each) and the nonce as a u64. The agent is the account that opens the channel: the session owner when the open goes through a session. It is not C.
- Receipt (`transcript.js`, `receiptMessage`): the 28 ASCII bytes `FLOP/COMPUTE_CHANNEL/RECEIPT`, the byte 1, the channel id, the final root, the aggregate G_n as a u128 and the payable as a u128. 125 bytes, not hashed. There is one receipt function and no rule on what payable is. The older form without the domain and the version byte is not written.
- Turn ack (`transcript.js`, `turnAckMessage`): the channel id, the turn index as a u32, the leaf hash, the agent's send time and receive time in milliseconds as u64. 84 bytes, not hashed. No rule on the order of the two times.
- Request (`session-auth.js`, `sessionRequestMessage` and `signSessionRequest`): the UTF-8 bytes of the compact JSON text of eight strings: `flop-session-request-v1`, the channel id as 0x hex, the method (`GET` or `POST`), the path, 0x hex of the blake2b 256 of the body's UTF-8 bytes, the time in milliseconds as decimal text, the 16 byte nonce as 0x hex, and the miner's challenge (64 lower case hex digits, no 0x). The path is one or more segments of a slash and letters, digits, `_` or `-`. A GET has the empty body. A body with a lone surrogate is refused. The headers are `x-flop-channel`, `x-flop-timestamp`, `x-flop-nonce`, `x-flop-challenge` and `x-flop-signature` (0x hex of the 64 byte signature).

What the chain has shown, and what it has not:
- Shown: the channel id for `force_open`, on three of the lab's records. `research/2026-11-11-session-escrow/results.json` (spec 1014014), the rerun's step A6 in `research/2026-11-12-session-rerun-1014020/results.json`, and step T3 in `research/2026-11-12-encoder-devnet-test/results.final.json`. `test/channel-id.test.ts` reads every input and every id from those files.
- Shown: the receipt, for two cooperative settles the chain took at spec 1014014 (`tzkv-runtime`): block 3479299 on channel `0x9f81f65b...` (the gateway's) and block 3479277 on channel `0x1fcd12cb...`. In each, the settle call's `agent_receipt_sig` verifies over the receipt under the `agent_key` the channel's record stores, with the payable equal to the channel's stored escrow. That escrow is the same in the record at the parent block and at the settled block, so the data does not tell before the settle from at it. Payable 0, the aggregate G_n, the escrow plus or less 1, the `miner_paid` of the `Settled` event, the older form without the domain and the version byte, one flipped bit and the other settle's signature do not verify. The fixture is the observatory's sixth recording, `observatory/fixtures/recording-20261114071524-9afba293ba8d1b2f/`, and the test is `test/channel-receipt-vector.test.ts`.
- What those two settles do not hold: every u128 in them is below 2^64, so the upper 8 bytes of the aggregate and of the payable are as the SDK describes them and are held by the layout's own tests alone.
- Not shown: that the chain checks that signature or refuses a settle signed over other bytes (no such settle was ever sent, and the pallet's source is not public); anything at spec 1014020 for the receipt; the payable of a settle that is not cooperative; the id for `open_channel` (inferred to be the same formula); the ack and the request against a miner. The id for `open_channel`, the ack and the request are as the SDK describes them.
- No rule is built on the miner's time window, its nonce rule or the life of a challenge. No source shows them.

The key:
- The library is `@scure/sr25519` at exactly 2.4.0. It signs under the substrate signing context, as FLOP's SDK does. Its signatures are randomized.
- `newChannelKey()` takes 32 bytes from the system's random source, makes the secret and the public key, and registers the seed, the secret and each half of the secret with the secret guard. The secret stays in a closure.
- The key is a frozen object of four functions: `publicKey()`, `signReceipt`, `signTurnAck` and `signRequest`. `JSON.stringify` of it is `{}`. It holds no channel id: each call names its channel.
- C signs those three layouts and nothing else. No function signs bytes it is handed, and none gives out the secret or the seed.
- Each signature is checked to be 64 bytes and to verify under the key's own public key before it is returned (`SELF_CHECK`). If the library throws while signing, the refusal says only that it threw (`SIGN_FAILED`). It carries no cause and no class name.
- `verifyChannelSignature` answers true only when the library's verify does. It answers false for a public key not 32 bytes, a signature not 64 bytes, or bytes the library throws on. It never throws on bytes, a detached array included (a detached array has 0 bytes).
- Everything `src/channel` and `src/plain-input.ts` export or return is frozen. Functions and classes are frozen with their prototypes and their methods, where they are defined.
- The shared freeze helper is `src/freeze.ts`: `deepFreeze` for objects and arrays, and `freezeFunction` for a function or a class, its prototype object and the methods and accessors on both (one level, own properties only). `src/chain`, `src/chain-read` and `src/channel` take it from there. It imports nothing, and both its functions are frozen. `src/plain-input.ts` keeps a local `freezeFn` that freezes a function and its prototype object only, because it imports nothing; that module exports no class, so it has no method to freeze.
- The identity point: the lab's verify refuses the identity point as a public key. The reference sr25519 accepts it with a zero signature for every message. C is never that key.
- `channelKeyFromSeed` makes the same key from a given seed. It is for tests alone: no file under `src` but `key.ts` names it, and a source scan holds that.

The boundary: these modules promise nothing against code already running in the process, which could replace the random source or the library. The secret guard keeps encodings of the seed and the secret for the life of the process, so that every writer refuses a copy.

C is never written. Tests that hold it:
- `test/channel-key.test.ts`: no view of the key (its keys, `JSON.stringify`, a spread, `util.inspect`) and nothing it returns holds the seed, the secret or a half of it in hex, base64, base64url or base58.
- `test/channel-secret.test.ts`: the secret guard flags them once a key exists; what the key returned, written through `writeJsonSafe` and `appendJsonlSafe`, leaves no copy of them in any file; and the secret itself is refused by both writers.
- `test/channel-source.test.ts`: no file under `src/channel` imports a file, socket, clock, environment, timer or store module, and none has a dynamic import.

The reference sr25519 for the tests is `@polkadot/wasm-crypto` 7.5.4 (Rust schnorrkel in WASM), with `@polkadot/util` and `@polkadot/x-randomvalues` 14.0.3, dev dependencies only (`test/lib/sr25519-reference.ts`). Nothing under `src` imports a package under `@polkadot/`. `test/channel-cross.test.ts` holds the lab's public keys equal to the reference's over 34 seeds, and each side's signatures verifying under the other.

## Miner client: the miner's words (not used by any command yet)

Ten files of `src/miner/` (P6a) hold the part of the miner client that has no I/O at all. It reads the miner's answers as text, rebuilds every hash those answers must match, verifies the signatures under a key the owner pinned, and holds the lab's own money bounds. No command uses it, and no file outside `src/miner` imports it yet. These ten files open no socket, read no clock, no environment and no file, and sign nothing. No miner was reached in building them. The HTTP file and the order of the calls are in the next section (P6b).

Why it matters: the channel key C signs a receipt that pays the miner the whole escrow (a cooperative settle pays all of it, S3). Everything the miner sends is its own word. FLOP's own client checks little of it, and nothing in it ties the money to the work: G_n is a number the miner states. So every word is checked here before C signs anything.

The files:
- `errors.ts`: the refusal codes `BAD_INPUT` (the caller's own input), `WIRE` (an answer not of its form), `PROOF`, `INFO`, `TURN`, `MONEY`, `RECEIPT`, and `MinerError`. `PROOF`, and `WIRE` of the proof, are exit 5; every other is exit 1. A message names the check that failed and the form wanted. It never carries bytes, hex or text of the answer or of the input.
- `forms.ts`: the forms a value is held to, and the hard maxima: a bounded text is 1 to 256 bytes of UTF-8, well formed, with no control character (U+2028 is allowed); the proof's image version and revision have their own form: 0 to 256 bytes of UTF-8, well formed, and control characters are allowed in those two fields and nowhere else; a turn's output is at most 2 MiB; `max_tokens` is 1 to 131072; a turn carries 1 to 256 messages and at most 1 MiB of input; a wire decimal has at most 39 digits.
- `check.ts`: the checks of a caller's input, as `src/channel` does them: plain fields of exactly the named ones, no accessor, bytes of the exact length as fresh copies, numbers as bigint inside their type. An extra field is refused without naming it.
- `expected.ts`: what the owner pins (below).
- `identity.ts`: the model identity hash, the message the enclave signs in the info proof, the turn evidence hash.
- `input.ts`: one chat turn's input as one value: the bytes, h_in and the max_tokens inside them. `verifyTurn` takes that value and nothing else about the input.
- `leaf.ts`: the version 3 leaf.
- `wire.ts`: the four parsers.
- `verify.ts`: the three verify functions.
- `money.ts`: the money bounds.

What the owner pins, and why (M-1, M-2). `minerExpected` takes the genesis hash, the miner account, the miner's enclave key and the model identity of eight fields (requested slug, registry model, registry version, model hash, precision, decode policy hash, measured root, backend model name). The info proof is signed by the enclave key about itself, and no chain entry holds a miner's enclave key, so a proof checked under the key the miner sent proves only that someone holds some key. The enclave key is therefore pinned by the owner in the run's config, beside the miner account and the endpoint. The owner gets it from the miner, who must agree to serve the lab anyway (S18). Every proof and every leaf is verified under the pinned key. There is no mode that takes the key from the miner's answer. The identity point (32 zero bytes) is refused as a pinned key before any signature is checked: the reference sr25519 takes it with a zero signature for every message (S46). A decode policy hash of all zero is refused: the lab pins a policy. The verify functions take only a value `minerExpected` made, and use a copy held apart, so a change to the arrays handed out changes nothing that is checked. The same holds for the parsers' values.

The parsers (`parseInfoProof`, `parseInfo`, `parseTurnReceipt`, `parseCloseAnswer`) each take the body text, read it through `readOutsideJson`, and read only the fields the lab needs:
- Hex is lower case and of the exact length. The proof's hex is bare, as the SDK's proof is. The info's, the receipt's and the close answer's hex has `0x`.
- A decimal is `0` or starts with 1 to 9, digits only, at most 39 digits, then held to its type. A number on the wire (the turn index, the precision) is a safe integer in range. A boolean is a boolean.
- The info's `minerAddress` is decoded from SS58 to its 32 bytes (any prefix, as the SDK compares bytes).
- A field that is needed and missing, of another type or out of its form is refused with `WIRE`. Extra keys are ignored and never echoed.
- An absent or null `settled` of the close answer is null, never 0.
- The info's `maxUnackedGn` is not read, in any form or when absent (M-20). The lab makes no use of it with one turn and one ack, and a field the lab does not need is not read.
- The proof's image version and revision may be empty (written with a zero length, as the SDK does) and may hold control characters. They are the miner's own text: they are shown only through `src/server-text.ts`, never as they are.
- The receipt must carry the provider fields whole (prompt tokens, completion tokens, finish reason, model identity) and the version 3 fields decode policy hash and h_ids (M-6). The sampling commitment hash (TOPLOC) may be absent or null: FLOP's client leaves it out when the miner has none (M-18). It then parses to null, never to 32 zero bytes, and the leaf takes 32 zero bytes for it, as the SDK's does. A stated hash is taken as stated, and a stated 32 zero bytes give the same leaf.
- Of `settled`, only the channel id and the transaction hash are read, as a hint for the provider. The miner's word on what was paid is not read: only the chain decides.

The checks:
- `verifyInfoProof`: the proof's genesis, account, enclave key and each identity field equal the pinned ones; ready is true; then the signature verifies under the pinned key over the message built from OUR challenge. It returns the image version and revision.
- `verifyInfo`: the miner address's bytes equal the pinned account; the enclave key, the model hash and each identity field equal the pinned ones; `is_ready` is true. It returns nothing: its only answer is that it did not refuse.
- `verifyTurn` takes `{expected, channelId, turn, receipt}`, where `turn` is a value `turnInput` made for the same pinned values as `expected`. An `input` or a `maxTokens` field, a turn `turnInput` did not make, and a turn made for other pinned values are refused (`BAD_INPUT`). Then, in this order, the first failure naming its check: the leaf version is V3; the turn index is 0 (one turn per run, M-4); h_in is the h_in of the turn value, the hash of the input bytes we sent; the decode policy is the pinned one and h_ids is not all zero; each identity field is the pinned one, the finish reason is `stop` or `length`, and completion tokens are at most the max_tokens of the input that was sent, held in the same turn value as the input bytes (there is no second number to hand in); the output is UTF-8 (decoded fatally) and does not start with the reserved prefix `FLOP-TURN-FRAMES-` that marks framed and tool outputs in the SDK; h_out is the evidence hash rebuilt from the output, the tokens, the finish reason and the pinned identity; the miner's done time is at or after its receive time and the latency is done minus receive; G_n is at most 2^64 minus 1; the running root is the leaf rebuilt from the fields (with one turn the root is the leaf); the enclave signature verifies under the pinned key over that leaf. It returns the leaf, G_n, the tokens, the finish reason, the sampling commitment hash as stated or null (null means none was stated, never zero bytes), the output as bytes and text, the three times and the enclave signature.

The money, all whole numbers of raw units, each a bigint inside a u128; a product or a sum past a u128 refuses:
- `turnCost`: refused (`MONEY`) when G_n is above `gnCeiling`, or when the floor (the escrow at open) plus the cost is above the budget. The cost is G_n times `pricePerGn` plus `basePerTurn`. Equal to the budget is accepted.
- `chainTariff`: `basePerTurn` times the turns plus the aggregate G_n, the chain's own bound.
- `receiptPayable`: refused (`RECEIPT`) when the payable (the escrow read back from the chain) is 0, above the budget, or below the chain's tariff. No other rule: how the floor counts toward the bill is not shown by any file (M-8).
- A cooperative settle pays the whole escrow. These bounds are the lab's only defence against a miner that states a large G_n for little work.

What is shown by a committed file: the version 3 leaf and its enclave signature, on the two real turns of the observatory's sixth recording (`observatory/fixtures/recording-20261114071524-9afba293ba8d1b2f/`, spec 1014014). For each, `leafV3` of the recorded fields equals the settle call's final root, and the enclave signature verifies over it under the record's enclave key (`test/miner-real-turns.test.ts`, `test/channel-verified-turn-vector.test.ts`). On both, done is after receive and the latency is done minus receive, so the timing rule holds on them.

What comes from FLOP's SDK 0.6.0 source only and is shown by no record (`dist/miner-admission.js`, `dist/compute-channel/transcript.js`, `protocol.js`, `transport-http.js`, `agent-client.js`, `chat-render.js`, read and not imported): the model identity hash, the info proof's message, the turn evidence hash, the canonical input and h_in, and every wire form of every answer. The layouts other than the leaf are held by three independent writings from the SDK's source: the code, the builder's test lib (`test/lib/miner-answers.ts`, `test/miner-cross.test.ts`) and the reviewer's test lib (`test/lib/review-p6a-*.ts`). That is still weaker than a real vector. The two real turns do not show the turn index's byte order, the upper bytes of G_n, h_in's or h_out's preimage, or any wire body.

What is unknown (M-17): every rule a real miner applies (the life of a challenge, its time window, its nonce rule, whether it needs checkpoints, JSON or frames, its error answers, whether it sends the provider fields and all three version 3 fields); the preimage of h_in and h_out on a real turn; a fold past one leaf; whether a real miner's leaf is version 3 at spec 1014020; where a trusted enclave key and a price come from other than the owner's own config.

## Miner client: the client that talks (not used by any command yet)

The second part of `src/miner/` (P6b) is the client that talks to a miner: the rule for an endpoint, the one file that makes HTTP calls, and the order of a run. No command uses it, and no file outside `src/miner` imports it yet: the provider (P7) will. It was built and tested against a scripted miner (`test/lib/scripted-miner.ts`), offline. No miner was reached in building it, and no real miner's address is known to the lab.

The files:
- `endpoint.ts`: `minerEndpoint(text)` makes the origin the client speaks to, a frozen value only it makes.
- `calls.ts`: the seven calls, each with its fixed method, path, time limit and byte limit, and `callLimits`.
- `requests.ts`: the body text of each request, written from what FLOP's SDK 0.6.0 sends.
- `timing.ts`: the two unsigned fields of the ack, as the SDK computes them.
- `http.ts`: the one HTTP file.
- `client.ts`: `minerRun`, the order of a run.
- `client-errors.ts`: the refusals `ENDPOINT`, `HTTP`, `ANSWER`, `ORDER`, `REQUEST`, `FAILED` and `MinerClientError`.

The endpoint (E1 to E3, M-11). Accepted: `https://host` or `https://host:port`, and `http://` only on the literal addresses `127.0.0.1` and `[::1]`, with or without a port, with or without one trailing `/`. `http://localhost` is refused with words that say to use 127.0.0.1: a name is resolved by the system and is no promise of loopback. `http://0.0.0.0` and `http://[::ffff:127.0.0.1]` are refused. Also refused: any other scheme, userinfo, a path, a query, a fragment, an empty host, a port out of 1 to 65535, a text over 2048 bytes, a control character or a space. The text is parsed with the platform's `URL`, and the origin rebuilt from the parts must equal the text but for one trailing `/`. So a host in another letter case, a default port written out, a dot segment, a percent escape or an IDN is refused, with words that ask for the plain form. Every endpoint refusal is exit 5. No refusal quotes the text.

The one HTTP file (T1 to T8, M-12). `minerHttp(endpoint, fetch)` takes the fetch as a parameter and gives a transport: one function from a request (the call, the body or none, C's signed headers or none, the byte limit, the time limit) to an answer (the status, the body or null, and the session challenge header). It is the only file under `src/miner` that names `fetch`, `Request`, `Response`, `AbortSignal`, `AbortController` or a timer.
- The URL is the origin and the call's fixed path: `/session/info-proof`, `/session/info`, `/session/open`, `/session/turn`, `/session/ack`, `/session/close`. No other path can be asked. `/session/checkpoint` and `/session/prepare-retirement` are not in the list (M-5, M-10).
- The headers are `Accept: application/json`, `Content-Type: application/json` with a body, and the five signed headers of `src/channel`, and nothing else. There is no headers option, no cookie, no authorization. Nothing reads the environment. The turn asks for JSON: streamed answers are refused (M-10).
- `redirect: "error"`, and a 3xx answer is refused. `credentials: "omit"`, `cache: "no-store"`, no referrer.
- One time limit for the whole exchange, body included. Defaults: the proof and the probe 10 s, the info, the open and the ack 30 s, the turn and the close 60 s. The hard maximum of each is 4 times its default. A caller may lower a limit, never raise it past the maximum.
- Byte limits: the proof 16 KiB, the info 64 KiB, the turn 8 MiB, the others 16 KiB. The bytes are counted while they stream, and the read stops and refuses past the limit. A Content-Length above the limit refuses before the body is read.
- Where a body is wanted (a 200 answer to the proof, the info, the turn or the close), the content type must be `application/json`, with an optional `charset=utf-8`, and the bytes are decoded as UTF-8 fatally. Otherwise the body is read to its limit and dropped, never decoded or parsed.
- No retry anywhere. A refusal names the call and what failed, the status as a number where there is one, never the body, a header value or the URL.

The order of a run (R1 to R7, M-9). `minerRun` takes the pinned values, the endpoint, a transport, the channel key C (handed in: this code never makes one), a clock, a random source and the limits. It holds its state in memory and writes nothing. Its only members are five steps, each allowed once and only in this order:
1. `prove()`, before anything is funded: a fresh 32 byte challenge, the info proof, a status of exactly 200, then P6a's parser and `verifyInfoProof`. It returns the image version and revision (the miner's own text: show it only through `src/server-text.ts`).
2. `authenticate({channelId})`, after the provider opened the channel: the anonymous probe must answer 401 with a challenge of 64 lower case hex digits; then the info signed by C with that challenge, a status of 200, `verifyInfo`.
3. `notifyOpen()`: the open notice, signed, with the channel id and C's public key. Any 2xx is taken.
4. `turn({messages, maxTokens, money})`: the turn, signed; a status of 200; P6a's parser, `verifyTurn` and `turnCost` with the money bounds handed in. Only then C signs the turn ack, with the buyer's send and receive times taken just before the turn call and just after its answer, and the ack is posted with the SDK's two unsigned fields (below). Any 2xx is taken.
5. `close({payable})`: only after the ack was taken. `receiptPayable` with the payable handed in (the escrow the provider read back from the chain), the budget, one turn and the turn's G_n. Only then C signs the one receipt of the run: the final root is the verified leaf, the aggregate G_n the turn's, the payable the one handed in. It is posted with the pinned measured root and a null transcript reference.

A step out of order, a step while another runs, and any step after a failure refuse and send nothing. C signs the requests the steps need (five in a whole run), one turn ack and one receipt. The tests count them through a wrapped key.

The ack's unsigned fields (R6). The SDK sends a timing status and a scored latency beside the signed ack (`transport-http.js`, `recordAck`), computed by `evaluateReceiptTiming` (`protocol.js`) with its defaults, a clock skew of 250 ms and a network pad of 100 ms. `timing.ts` computes them the same way from the times the run holds: Eligible with the smaller of the buyer's latency and the miner's latency plus 350 ms, or Ambiguous with the miner's latency when the buyer's latency plus 350 ms is below it. The SDK signs no ack whose timing is Invalid: the buyer's clock reversed, the miner's clock reversed, or a latency that is not done minus receive. Those refuse before C signs.

What `close` returns (R3). Once C has signed the receipt, `close` does not throw: the signed receipt is public data the provider must keep whatever the miner answers. It returns the receipt (its fields and the signature) and the answer as one of three states:
- a hint: the miner named our channel id and a transaction hash;
- no hint: a 200 answer with no `settled`;
- unknown, exit 6, with the reason: any failure of the call, a status other than 200, an answer not of its form, or a `settled` naming another channel.
None of the three is read as settled or not settled. Only the chain decides.

Exit codes (R5, M-15), none new:
- 5: an endpoint refusal; a status other than 200 for the proof; a proof not of its form; a false proof.
- 11: the proof call gave no answer (a transport failure, a time limit, a body over its limit, a redirect, a type or an encoding). Nothing is funded yet.
- 1: any refusal or failure of steps 2 to 4, a step out of order, and a payable out of the bounds at step 5.
- 6: the unknown of step 5.

No refusal and no returned error holds a prompt, an output, a signature or a key. The values returned are the verified turn (its leaf, enclave signature, tokens, times and output), its cost, the signed ack and the signed receipt. C's secret is never reachable from them.

What is not known (M-17): every rule a real miner applies (the life of a challenge, its time window and its nonce rule; whether it needs checkpoints; whether it answers JSON or streams frames; its statuses and error answers; whether it takes our ack and our signed requests); whether it serves a channel opened through a session; whether its close settles with a payable equal to the escrow. Every answer the tests use is synthetic.

## Known gaps

- **Redacted receipts never settle.** A receipt body with a key shaped field is redacted, and a redacted receipt never proves a settlement. Per the gateway's documented receipt schema (OpenAPI CredentialReceipt, read 2026-11-11), the fields imd-flop stores are `request_id`, `correlation_id`, `state`, `reserved_spend`, `settled_spend`, `settled_spend_raw` (decimal digits), `terminal_event` and `channel_id` (both on the public hex allowlist). Only `settled_spend_raw` can be key shaped within that schema: it is decimal digits with no length limit, so a value of 64 or more digits matches the 64 hex rule. An exact amount below 2^128 has at most 39 significant digits, so that takes 25 or more leading zeros, or a value at or above 2^128, which is not an exact amount anyway. Such a receipt is stored with `settled_raw` redacted, never settles, and its call stays charged at its hold: the safe direction. Any other receipt that follows the schema is stored whole and can settle. This has not been seen on a live settled receipt yet. If a live receipt did carry a key shaped field, its call would stay charged at its reservation: the padded quote, or the reported cost when that is higher.

## Open questions

- **Who pays** for FLOP calls on testnet and mainnet: imd requesters or seat holders? Still open. Until that's answered, `payer` is a config switch that labels a call and adds a job budget. The switch does not remove the daily cap: the seat's key pays for every call today, so every call counts against it.
- **Testnet** has no date, and its identity requirements (did:key, SS58 sr25519/ed25519, or both) are unpublished. Only `devnet` is accepted.
- **Explorer URL formats** for FLOP sessions and settlements aren't documented, so receipts don't link to the explorer yet.
- **InferenceReceipt** (in the OpenAPI) hasn't been seen on a real response yet, so no receipt is ever marked chain-final.
- The link statement format and its EIP-712 domain (`imd-flop seat link`, chainId 1, the seat collection) are ours until imd adopts one.
- The owner check reads `eth_chainId`, then `ownerOf` at `latest`, through an RPC you supply. The chain id must be 1, the chain of the seat collection in `src/networks.ts`. Plain `link verify` skips the RPC unless you pass one. A paid run requires it. The check runs when a run starts, so after a sale the link dies at the next run, not the moment the seat changes hands. Only normal (EOA) wallets are supported, not smart wallets like a Safe (ERC-1271). The supplied RPC is trusted for the chain id it reports. Its URL often carries a key, so no message quotes it: a URL that is not a valid http(s) URL is refused before any request. Nothing the RPC server or its transport says is quoted either: a failure is a kind and numbers only. In other text that might repeat the URL, it shows as `[ETH_RPC_URL]`.
- The link statement stores the devnet genesis hash pinned in `src/networks.ts` (the full `faucet.flop.network/chain` value read on 2026-11-09). `verify` compares the statement to that pin. A paid run also reads the live faucet and the RPC block 0 and continues only when both equal that same full pin. A reset that moves both to a new hash fails the check while this program still carries the old pin. `init --check-genesis` is the optional form of the live comparison; a paid run always runs it. The device-key vouch in `DEVICE-KEY-PROPOSAL.md` is still a design note and is not built here.
- Proposed for the version imd would ship (not built here): imd already binds an Ed25519 device key to each seat with the holder's EIP-712 signature (`GET https://api.imd.fun/pair/wallet/:address`). Having that device key sign the FLOP DID would mean holders sign nothing new, and re-pairing or selling the seat revokes the link. The FLOP key stays separate; the device key only vouches for it.
